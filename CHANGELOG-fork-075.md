# Changelog — `fork-075`

Changes on top of `6c573139` (the import of upstream `zeroclaw-labs/zeroclaw v0.7.5 @ a2988f0d`). Range covered: `6536817c..HEAD`.

## Summary

| # | Commit | Type | Area | What changed | Why |
|---|---|---|---|---|---|
| 1 | [`6536817c`](../../commit/6536817c) | ci / docker | build | `.github/workflows/build-ghcr.yml` triggers on `push` to `fork-075` (plus `workflow_dispatch`), builds `Dockerfile.debian`, and pushes a single immutable tag `ghcr.io/<repo>:fork-075-<sha7>-debian`. `Dockerfile.debian` runtime stage gains `python3` + `python3-pip` + `python3-venv`. | The v0.7.5 overlay wiped the warden-protocol generic GHCR workflow, so fork-075 had no automated container builds. Unlike fork-074, no other `Dockerfile.debian` patches were needed: upstream rewrote Stage 1 in v0.7.5 with explicit stub-cache invalidation (`rm -rf target/release/.fingerprint/zeroclaw-* …` between the two cargo builds) and selective `tools/`/`xtask/` manifest copies — superseding the six docker fixes we layered on fork-074 to make the same Dockerfile build end-to-end. Python toolchain install is still warden-only (forwarded from fork-074 row 7). |
| 2 | [`af3b0652`](../../commit/af3b0652) + [`167dcd22`](../../commit/167dcd22) + [`b35fe28f`](../../commit/b35fe28f) | fix / feat | observability | Ported from `fork-074` row 2 (which itself was ported from `fork-073` row 3). Introduced `observability::shared_observer()` (process-wide `Arc<dyn Observer>` via `OnceLock`) and routed every subsystem through it: gateway, channels orchestrator, `Agent::from_config_with_session_cwd_and_mcp`, `run_agent_loop`, `agent::process_message`, and the heartbeat worker. `BroadcastObserver` switched from `Box` to `Arc<dyn Observer>`. `WebhookChannel` gained an optional observer (`with_observer`) and now records `ChannelMessage{channel="webhook", direction=…}` on inbound and outbound traffic. `process_channel_message` now also emits a top-level `AgentStart` before the LLM call and `AgentEnd` after `run_tool_call_loop` returns. Conflicts on v0.7.5 base: (a) `from_config` was split into a thin wrapper + `from_config_with_session_cwd_and_mcp` — applied `shared_observer` inside the extended method, kept upstream's session-cwd plumbing; (b) the orchestrator's tool loop now sets up a `tool_receipts_collector` / `receipt_scope` immediately before the LLM call — kept both, with `AgentStart` recorded right after. | Each subsystem used to build its own `PrometheusObserver`, leaving them with separate registries — events recorded in one were invisible to the `/metrics` endpoint exposed by another. The orchestrator's tool loop also only fired `LlmRequest`/`LlmResponse` and `ChannelMessage`, so `zeroclaw_agent_starts_total` and `zeroclaw_agent_duration_seconds` stayed empty for any message arriving through a channel. Now the whole process records into one Prometheus registry and channel-driven invocations show up as agent runs. |
| 3 | [`fd7caacd`](../../commit/fd7caacd) + [`d2492802`](../../commit/d2492802) | fix | orchestrator / webhook | Ported from `fork-074` row 3 (originally `fork-073` row 4). Added `Channel::notify_no_reply(reply_target, thread_ts, reason)` to the `Channel` trait (default no-op so chat channels don't post the reason as a bot message). `WebhookChannel` overrides it to reuse the existing reply schema — the LLM-supplied reason becomes `content` (or `"(no reply)"` when absent), `thread_id` / `recipient` are preserved. The orchestrator's NoReply branch now invokes it before returning, alongside the existing trace event and stdout log. | Resolves [warden-protocol/basedai#872](https://github.com/warden-protocol/basedai/issues/872): when the reply-intent precheck classified an inbound webhook message as `NO_REPLY`, the orchestrator silently dropped it and the API caller received nothing — indistinguishable from a still-in-flight or dropped request, forcing downstream consumers to time out. |
| 4 | [`e370b014`](../../commit/e370b014) | feat | channels / config | Ported from `fork-074` row 4 (originally `fork-073` row 5). Added `[agent.precheck]` config section (`ChannelPrecheckConfig`) with three knobs: `enabled` (kill-switch, default `true`), `model: Option<String>` (default `None` → falls back to the route model), and `timeout_secs` (hard ceiling, default `5`). The channel orchestrator's reply-intent classifier wraps `classify_channel_reply_intent` in `tokio::time::timeout`, fails open to `REPLY` on both error and timeout, and emits a structured `elapsed_ms` / `model` log on completion. When `enabled = false` the precheck is skipped entirely. | Mirrors the existing `ContextCompressionConfig.summary_model` pattern so operators can route the lightweight REPLY/NO_REPLY classifier to a faster/cheaper model than the main reasoning model. The timeout was prompted by a field incident where a Venice precheck silently took 57s. |
| 5 | [`d6fd546b`](../../commit/d6fd546b) + [`55c4a76b`](../../commit/55c4a76b) | fix | gateway / runtime | Ported from `fork-074` row 5. Introduced a process-wide broadcast hook in `zeroclaw-runtime::observability` that any factory-built observer fans events out to. The gateway installs the hook on startup; the agent loop keeps building its own primary observer per call but now tees into the hook automatically. `BroadcastObserver` became a pure broadcaster (no inner wrap) and `pub(crate)` to the gateway; `prometheus_observer_from_state` simplified to a single direct downcast. Follow-up swapped the hook's `std::sync::RwLock` for `parking_lot::RwLock` to drop `.unwrap()` from every event-recording site. | Tool-call and other observer events emitted inside `process_message` never reached SSE subscribers because the gateway's `BroadcastObserver` only wrapped the per-state observer — each `create_observer` call (notably in the agent loop) returned a fresh, isolated backend, so events from channels and webhooks logged to Prometheus but were silently dropped at the `/api/events` boundary. The `parking_lot` swap removes panic-on-poison on the hot path. Closes [#6526](https://github.com/zeroclaw-labs/zeroclaw/issues/6526). |
| 6 | [`9608ed81`](../../commit/9608ed81) | fix | cron / channels | Ported from `fork-074` row 6. Added optional `thread_id` to `DeliveryConfig` / `DeliveryConfigDecl` (backward-compatible JSON), threaded it through `convert_delivery_decl`, the `DeliveryFn` typedef, `deliver_if_configured`, `orchestrator::deliver_announcement`, and every caller. Chained `.in_thread(thread_id.clone())` on every `SendMessage::new` in `deliver_announcement`. Made the cron hint in `build_channel_system_prompt` channel-aware. Conflicts on v0.7.5 base: (a) upstream moved `register_delivery_fn` out of the `daemon` branch into a top-level `#[cfg(feature = "agent-runtime")]` block before the command match (so `gateway start` also has a delivery handler) — extended that registration's closure signature to carry `thread_id` through, removed the duplicate registration the patch tried to add inside `daemon`; (b) upstream added `.with_workspace_dir(...)` to the Discord channel constructor in `deliver_announcement` — kept the workspace-dir call and the `make_msg(...)` helper so `thread_id` still rides along. | Cron `announce` deliveries dropped `thread_id` on the way out — most visibly on the webhook channel, where downstream services that route on `thread_id` discard callbacks that arrive without it. Fixes [#6634](https://github.com/zeroclaw-labs/zeroclaw/issues/6634). |
| 7 | [`4b2079d9`](../../commit/4b2079d9) | feat | tools | Ported from `fork-074` row 8. Added a config-gated `file_upload` tool (`crates/zeroclaw-tools/src/file_upload.rs`) that ships a file from the agent's local filesystem to an HTTPS endpoint via `multipart/form-data` without ever loading the bytes into model context — the LLM passes only a file path; the host reads, validates, and uploads. The `[file_upload]` config section follows the `[mcp.servers.*]` shape. Path access goes through the same `SecurityPolicy` hooks `file_read` uses, the autonomy gate blocks read-only mode, and the rate limiter debits the action budget before any network call. | Lets the agent hand off large artifacts (logs, generated assets) to external sinks without paying the round-trip through model context — keeps the LLM's working set bounded and avoids re-tokenising binary blobs for transport. |
